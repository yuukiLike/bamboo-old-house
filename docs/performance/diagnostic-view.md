# 页面内诊断进度与完整时间线

用户选择：只在诊断模式显示，不改变普通访客的加载界面。

## 打开实时面板

生产预览服务启动后，在 Chrome Canary 打开：

```text
http://127.0.0.1:4175/?perf=1&perfUI=1
```

`perf=1` 开启阶段记录；`perfUI=1` 额外显示面板。只使用 `perf=1` 的批量采集不显示面板。面板动态导入，复用项目已有的 [Base UI Progress](https://base-ui.com/react/components/progress)，不再安装另一个进度条库。

面板展示三类信息：

- **正在执行**：阶段名称、已等待时长、不确定进度条。下载、编译等无法预知最终耗时，不显示虚假的完成百分比。
- **完成的时间条**：导航、资源和业务阶段的实际起点与时长。模型下载、解析、场景构建、着色器准备、预热、首帧提交等分别保留；能够检索原始 phase 名称。
- **进入页面之后**：继续保存视图切换、首次室内管线、声音下载与解码等记录；支持导出本地 JSON。

时间统一相对本次导航的 `performance.now()` 原点。首屏控件就绪时间取 `startup.controls-ready`，它表示 React 提交后控件已启用，**不等于画布淡入结束、GPU 完成或屏幕首次呈现**。外部采集器另外检查画布淡入完成，报告中的“近似就绪”包含驱动轮询延迟。两种边界不会合并成一个看似精确的数字。

父阶段包括子阶段，多个模型可能并行加载，因此时间条不能相加为总耗时，也不能把“完成了几条记录”当作整体加载百分比。

## 主线程卡住时会发生什么

页面内的 React 面板也运行在主线程。同步场景构建、某些渲染调用阻塞时，它无法持续刷新；任务结束后会回填完整阶段耗时。面板没有为了刷新而改变加载顺序或给原业务插入 yield。

导航初期的 HTML、脚本和样式请求发生在面板加载之前，面板可在启动后从 Performance API 回填。它不能在自己的 JavaScript 尚未下载时就显示实时进度。资源缓冲和阶段记录有容量限制，缺失、截断和失败不能解释为耗时为零。

这也是完整报告仍然必需的原因：外部探针在导航前安装，记录 RAF 长间隔、长任务和业务事件；诊断 trace 则用于核对主线程调用栈。

## 打开完整报告

```sh
# 先设置 PERF_CHROME 与 PERF_DRIVER，见 scripts/perf/README.md
pnpm perf --flow views --profile desktop --mode diagnostic --iterations 1 \
  --out outputs/performance/desktop-views-diagnostic
```

打开产物中的 `report.html`：先看顶部“卡顿位置”，再展开首屏轮次中的统一时间线。导航从 0 ms 开始，浏览器阶段、业务阶段、资源与 RAF 停顿共用同一横轴；重叠不代表因果，调用栈用于进一步归因。各按钮操作保留自己的观察窗口和状态快照。

为了评估平常体验，另用 `--mode baseline --iterations 3`。面板显示与否、trace 开关、浏览器版本、画布尺寸、声音和天气状态均会影响结果；报告核对配置和逐场景状态后才允许输出前后差值。打开实时面板的录制不能与隐藏面板的录制计算产品优化收益。
