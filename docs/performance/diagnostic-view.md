# 运行时实时监测、加载进度与完整报告

用户选择：只在诊断模式显示，不改变普通访客的加载界面。

## 打开实时面板

生产预览服务启动后，在 Chrome Canary 打开：

```text
http://127.0.0.1:4175/?perf=1&perfUI=1
```

`perf=1` 开启阶段记录；`perfUI=1` 额外显示面板。只使用 `perf=1` 的批量采集不显示面板。面板动态导入，复用项目已有的 [Base UI Progress](https://base-ui.com/react/components/progress)，不再安装另一个进度条库。

面板默认打开 **实时运行**，可切换回 **加载时间线**。折叠面板或切换页签不会停止实时采集；显式暂停、页面隐藏或卸载面板才会停止。

## 实时运行

实时页提供：

- **近 5 秒 RAF 回调率、p95 与最大间隔**：统计最近 5 秒内结束的完整前台 RAF 间隔。跨窗口起点的长间隔仍保留完整时长，因此样本间隔合计可能超过 5 秒；不会把一次 6 秒卡顿裁成 5 秒或在恢复时漏掉。
- **近 30 秒图**：每 200 ms 桶保留最大间隔，按结束时刻定位。50 / 100 ms 为诊断分级，颜色对应慢间隔与更长停顿；柱高最多显示到 500 ms，超长值在数字、详情和悬停提示中完整保留。
- **最近卡顿**：导航后的起点、完整时长、附近场景 / 地点 / 声音 / 天气状态、期间真实控件操作和重叠业务阶段。另列间隔开始前 2 秒内最近一次操作及相隔时长，便于追踪异步转场；它不是因果判定。默认最近 6 条，可展开最多 120 条保留记录。
- **渲染器快照**：draw calls、triangles、纹理 / 几何体数量、绘图尺寸、pixel ratio 和图形后端。来自应用已有诊断，每 15 个应用帧更新；数量不是显存字节。
- **主线程长任务**：支持 Long Tasks 的浏览器显示近 5 秒内结束的任务数量与最长时长；不支持时明确说明，不填零。

`暂停采集` 冻结读数和时间轴，`继续采集` 从新边界开始；切到后台也停止取样，恢复时不计跨隐藏边界的间隔。`清空窗口` 清除实时历史，保留加载时间线，且不会擅自解除手动暂停。`导出 JSON` 包含 `runtime` 快照、已保留卡顿和长任务，以及原有加载阶段和资源数据。

每 250 ms 刷新一次 UI，RAF 原始历史保留最近 30 秒并设置 12,000 条容量上限；卡顿与长任务分别最多 120 条，容量覆盖有计数提示。状态不是逐帧精确追踪，操作与阶段只保存有界线索：最近最多 120 次操作，每个卡顿最多 12 个重叠阶段。阶段中的 `running` 表示发现该卡顿时尚在进行，不能当作当前仍未结束。尚未结束的 RAF 间隔只有在下一次回调到来后才能确定。

采集器从诊断面板挂载后开始，不能补录此前的帧。它不改渲染循环，不测 GPU 时间或真实屏幕呈现；**RAF Hz 不是屏幕 FPS**。暂停产品动态也不等于停止 RAF。适配器的场景状态与重叠线索用于定位，不能单独证明卡顿原因。正常批量基线仍使用隐藏面板配置，避免加入实时图和 DOM 刷新的开销。

## 加载时间线

加载页保留三类信息：

- **正在执行**：阶段名称、已等待时长、不确定进度条。下载、编译等无法预知最终耗时，不显示虚假的完成百分比。
- **完成的时间条**：导航、资源和业务阶段的实际起点与时长。模型下载、解析、场景构建、着色器准备、预热、首帧提交等分别保留；能够检索原始 phase 名称。
- **进入页面之后**：继续保存视图切换、首次室内管线、声音下载与解码等记录；支持导出本地 JSON。

时间统一相对本次导航的 `performance.now()` 原点。首屏控件就绪时间取 `startup.controls-ready`，它表示 React 提交后控件已启用，**不等于画布淡入结束、GPU 完成或屏幕首次呈现**。外部采集器另外检查画布淡入完成，报告中的“近似就绪”包含驱动轮询延迟。两种边界不会合并成一个看似精确的数字。

父阶段包括子阶段，多个模型可能并行加载，因此时间条不能相加为总耗时，也不能把“完成了几条记录”当作整体加载百分比。

## 主线程卡住时会发生什么

页面内的 React 面板也运行在主线程。同步场景构建、某些渲染调用阻塞时，它无法持续刷新；任务结束后会回填完整阶段耗时。面板没有为了刷新而改变加载顺序或给原业务插入 yield。

导航初期的 HTML、脚本和样式请求发生在面板加载之前，面板可在启动后从 Performance API 回填。它不能在自己的 JavaScript 尚未下载时就显示实时进度。资源缓冲和阶段记录有容量限制，缺失、截断和失败不能解释为耗时为零。

这也是完整报告仍然必需的原因：外部探针在导航前安装，记录 RAF 长间隔、长任务和业务事件；诊断 trace 则用于核对主线程调用栈。

## 打开完整报告

```sh
# 先设置 PERF_CHROME 与 PERF_DRIVER，见 scripts/perf/README.md
pnpm perf --flow views --profile desktop --mode diagnostic --iterations 1 \
  --out outputs/performance/desktop-views-diagnostic
```

打开产物中的 `report.html`：首页先看关键数字和各场景横条对比，通过导航进入首屏时间轴和重点卡顿。完整原始表保留在折叠详情里。导航从 0 ms 开始，浏览器阶段、业务阶段、资源与 RAF 停顿共用同一横轴；重叠不代表因果，调用栈用于进一步归因。各按钮操作保留自己的观察窗口和状态快照。

为了评估平常体验，另用 `--mode baseline --iterations 3`。面板显示与否、trace 开关、浏览器版本、画布尺寸、声音和天气状态均会影响结果；报告核对配置和逐场景状态后才允许输出前后差值。打开实时面板的录制不能与隐藏面板的录制计算产品优化收益。
