# Tidewater 优化策略在竹林老屋中的迁移

日期：2026-09-26。分支：`perf/tidewater-scene-optimizations`。

系列入口：[3D 性能优化记录](../optimization-log.md)。这是系列第一阶段，后续阶段使用相同分支前缀和递增编号。

基线提交：`3f382ac0fb84e35ca52593e2630c660c078d723d`。用户已确认优化当前竹林老屋项目。

来源：[Tidewater 源码分析报告](../../research/tidewater-performance-analysis.md)。本次目标是当前 `bamboo-old-house`，迁移适用的策略，不移植 Tidewater 自有 WebGPU 引擎。

## 优化前记录

以下假设与验收方式在改动产品代码前保存。

现有项目已经有实例化、静态远景 LOD、阴影植被分块、非投影植被逐实例裁剪、风力缓存、房间点光源阴影缓存和异步预热。Tidewater 的 FFT 海面、云层时间复用、TAAU 不适合直接套在此场景；其底层缓冲缺陷也不属于 Three.js 本项目。

### 1. 遮雨查询的空间索引

依据：[首次采集](../first-capture.md) 将启动时的长任务定位到 `weatherSurfaces → shelter.exposure → exact.blocked`。历史 `scene.weather-build` 约 5–6 秒只是定位线索，不能与本次 Node 测量或不同浏览器的结果直接比较。

原实现：对静态建筑三角形建立通用三维层次包围盒；大量表面顶点以三个固定雨向发射射线，每次遍历包围盒和候选三角形。已有 10 厘米量化缓存，不能再通过降低精度来省查询。

待验证方案：借鉴 Tidewater 的空间局部查询和预计算，利用只有三个固定雨向这一约束，建立方向投影网格作为三角形候选索引。候选仍使用原来的精确三角形求交、12 米范围和自交阈值。与原实现和独立暴力求交对照；若候选膨胀或启动总耗时没有下降，则保留试验记录并放弃该方案。

### 2. 植被裁剪与实例上传

原实现：相机矩阵变化后，对每个非投影植被批次的全部实例逐个做视锥检测；只要可见列表变化，就重写并上传全部可见矩阵和颜色。

待验证方案：借鉴 Tidewater 的空间分块查询，先测单元包围盒，只对边界单元检查实例；保持源实例顺序、风偏移边界和阴影投射规则。对可见列表只上传实际改变的连续区间，避免数量缩小时上传未变的前缀。

### 保持与验收

- 保持画布 DPR、抗锯齿、植被数量、LOD 阈值、阴影尺寸、材质、雨量与相机行为。
- 用真实建筑 GLB 的纯代码基准比较启动查询，用确定性相机路径比较植被裁剪；保存逐轮时长、输出哈希和差异数量。
- 新增测试覆盖薄墙 / 缝隙 / 变换 / 射线距离边界，以及植被移动、投影、矩阵颜色对应和更新范围。
- 运行 `pnpm check` 和 `pnpm build`，启动本地生产预览供用户查看。
- 遵守本轮“不要使用 computer-use”：本次不操作浏览器界面。纯 CPU 基准只能证明相应计算的收益，不能当作整页 FPS、GPU 帧时或视觉验收结果。

## 实施与复测

已实现两项优化，保留原画质配置。本次没有增加运行时依赖、修改模型资产或修改 shader。

### 实际改变

**遮雨查询**：[rain-occlusion.ts](../../../src/components/scene/rain-occlusion.ts) 针对三个固定雨向，使用 `u = x - (dx/dy)y`、`v = z - (dz/dy)y` 将平行射线投影为一个点。三角形的投影包围盒加入 0.125 米网格；查询只访问对应单元，再执行原有 Three.js 精确求交。候选按最低高度排序，超出射线范围时提前结束。最终索引用连续的 `Uint32Array` 保存偏移与三角形 ID，避免长期保留数万个小数组对象。

[rain-shelter.ts](../../../src/components/scene/rain-shelter.ts) 接入新索引。10 厘米查询缓存、8 毫米法线偏移、12 米射线长度、自交排除阈值、屋顶高度场、雨水衰减和体素碰撞均保持原值。网格大小只控制候选数量，不量化交点，不会把细缝当成实体。此查询仍只在静态湿润属性构建和显式诊断时运行。

**植被裁剪**：[vegetation-visibility.ts](../../../src/components/scene/vegetation-visibility.ts) 为非投影植被建立 8 米空间单元，每个单元包住包含风偏移余量的全部实例球。整个单元在视锥外就跳过，在视锥内就直接接受，边界单元继续逐实例精确检测。仍扫描可见标记以保持原始实例顺序，复杂度不是完全脱离实例数的 O(1)。投影植被沿用原来的 16 米分块，屏外投影物不会被眼睛视锥错误剔除。

可见列表变化时只重写不同的区间；仅删除末尾实例时只缩短 `mesh.count`。更新范围累积到真实 GPU 上传后由 Three.js 清除，因此同一帧多次相机更新也不会丢失尚未上传的区间。矩阵、颜色和以根位置计算的风动画保持对应。

### 测量口径

脚本：[optimization-bench.mjs](../../../scripts/perf/optimization-bench.mjs)。环境：Apple M4、macOS Darwin 27.0.0、Node v24.18.0、Three.js r185。每个版本独立执行 3 轮，没有浏览器或 GPU 渲染。

- 建筑测试使用真实 `architecture.glb`，996,363 个三角形；执行生产代码中的 `stabilizeHouseSurfaces`、屋顶高度场、遮雨索引、体素碰撞构建和 `weatherSurfaces`。计时表中的“合计”从遮雨索引开始，到建筑表面湿润属性完成；不包含模型下载、贴图解码、屋顶高度场、其他场景物体、shader 编译或渲染。
- 表面输出含 1,131,197 个顶点的 `rainExposure` 与 `rainIngress`；实际使用到侧向进雨的顶点为 114,408，两版一致。
- 植被测试是确定性压力夹具：3 万实例、180 帧相机旋转/移动/变 FOV/静止路径，比较完整可见顺序、矩阵、颜色及请求上传字节。它不是实景整页帧率测量。
- 同时保存每轮数据与中位数，未删除较慢首轮。两版环境及 GLB SHA-256 相同。优化后记录的全部产品源码指纹已与工作区逐一核对。

### 最终同条件结果

| 指标 | 原版三轮中位数 | 优化后三轮中位数 | 变化 |
| --- | ---: | ---: | ---: |
| 建筑遮雨 + 表面湿润属性 CPU 合计 | 5,763.08 ms | 3,819.58 ms | **−33.72%** |
| 其中：表面湿润属性计算 | 5,029.18 ms | 2,599.62 ms | −48.31% |
| 其中：遮雨索引 + 体素构建 | 731.25 ms | 1,219.96 ms | **+66.83%** |
| 植被 180 帧裁剪 CPU 合计 | 62.41 ms | 39.42 ms | **−36.82%** |
| 植被每帧平均 CPU | 0.347 ms | 0.219 ms | −36.82% |
| 各轮植被 P95 耗时的中位数 | 0.564 ms | 0.405 ms | −28.20% |
| 植被空间结构初始化 | 2.90 ms | 5.41 ms | +86.23% |
| 180 帧请求上传字节 | 73,113,900 B | 73,015,100 B | −0.14% |

每一行独立取中位数，分项中位数不保证相加等于合计中位数。遮雨合计原版三轮是 `6909.61 / 5663.73 / 5763.08 ms`；优化后是 `4266.37 / 3396.16 / 3819.58 ms`。植被裁剪合计原版为 `59.10 / 62.41 / 62.46 ms`；优化后为 `41.44 / 39.42 / 35.41 ms`。

上传优化在这条移动路径上收益很小：稳定的源顺序中插入/删除一个可见实例，仍可能移动后续大量槽位。因此不宣称“大幅减少 GPU 上传”，也不将裁剪省下的约 0.128 ms/帧描述为解决了整页低帧率。

请求上传字节按版本号变化和 `updateRanges` 计算，未创建 WebGL 上下文，不包含首次完整缓冲分配或驱动实际传输统计。

新方向索引的已知数组容量为 **88,085,980 字节，约 84.01 MiB**，含顶点、Y 边界、偏移表与 10,926,248 个候选引用，覆盖 79,920 个非空单元。这不包括临时构建对象、其他场景资源和进程开销；本次没有测浏览器内存峰值，也未证明整体内存下降。原版也持有顶点、ID 和三维树节点，因此不能仅凭数组大小推断两版总内存差。移动端峰值内存仍需实际预览/设备采集确认。

### 放弃的试验与边界

第一次 0.5 米方向网格试验，在未调用墙面微调的几何摸底夹具中，CPU 合计为 10,203.08 ms，同夹具原版首轮为 6,705.75 ms。输出哈希一致，但候选集合太大，比原版慢，已放弃。细化至 0.125 米后才继续实施。

中途 0.125 米试验及“小数组打包”版本曾得到约 40% 的合计降幅；最终加入与产品一致的墙面微调、改为连续索引数组并重新采集后，以本页 **33.72%** 的最终结果为准。所有本地中间样本保留于 `outputs/performance/tidewater-transfer/`，不把不同夹具的数字混算。

本轮没有引入基于帧率的自动降分辨率，也没有降低阴影更新频率。它们会影响竹叶采样或动态影子，缺少浏览器视觉验证时不宜与本次输出等价的改动混在一起。

### 复现 CPU 采集

在项目根目录依次执行，每次使用新输出文件名；脚本拒绝覆盖已有证据：

```sh
node scripts/perf/optimization-bench.mjs \
  --ref 3f382ac0fb84e35ca52593e2630c660c078d723d \
  --out outputs/performance/tidewater-transfer/recheck-before.json

node scripts/perf/optimization-bench.mjs \
  --out outputs/performance/tidewater-transfer/recheck-after.json
```

运行时只启动一个采集进程，避免同时构建或执行其他压力测试。默认 3 轮；`--iterations 1` 仅适合试验。脚本只切换读取的源码快照，不切换主工作区分支；模型使用当前工作区的 GLB，输出记录其哈希，比较时应核对相同资产与环境。
