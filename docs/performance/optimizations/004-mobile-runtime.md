# 第四阶段：移动端持续运行、停止检测与清晰度

## 范围与问题证据

- 分支：`perf/tidewater-scene-optimizations-04-mobile-runtime`，从合并 PR #8 后的 `main` 提交 `8a9033d` 创建。
- 用户反馈：iPhone 16 Pro，Safari 与 Chrome，在 `perf=1&perfUI=1` 模式开启声音并游览，约 30 秒后读数降至 11–13，手机开始发热。
- 本阶段检查采集记录、音频资源与共用渲染循环；新增停止全部检测的按钮，提高移动端默认清晰度。声音、雨量、模型、遮雨精度、材质及风动公式保留。
- 先分析源码，再使用独立的桌面 Chrome Canary 会话做移动视口验证。**桌面模拟不具备 iPhone 的温度、功耗与驱动条件，不能据此宣布真机热降频已经解决。**

## 排查结论

### 未发现采集记录无限增长的证据

原实现已经限制：业务阶段 500 条、活动阶段 100 条、资源 500 条、卡顿与长任务各 120 条；RAF 历史按最近 30 秒淘汰，并另有 12,000 条上限。场景诊断帧数组最多 15,000 条。

回归测试按 12.5 Hz 连续模拟 30 分钟：RAF 历史不超过 377 条，卡顿保留 120 条。原实现通过这个有界性检查，因此没有将“限制数据容量”虚构成本次修复。

在原版桌面 Canary 的约 75 秒声音＋视角切换观察中，基础录音解码总量保持 **90,687,280 字节**，没有随着循环重复解码；声音源会在结束时断开并从 Map 删除。观察到的同时保留源为 4–6 个，包含交叉淡入淡出与提前调度。新版本观察中为 4–7 个，解码总量相同。该数字是已解码 PCM 的估算容量，不能直接当作 JS 堆或进程总内存。

原版在采样末尾主动 GC 后 JS 堆约 49.49 MB，新版约 50.14 MB。GC 前堆大小有波动，不能仅凭短期上涨判定泄漏；这也不证明所有真机资源都没有泄漏。夜景首次出现时纹理从 134 增至 143、几何体从 265 增至 266，随后返回视角保持稳定，符合一次性资源分配的观察。

### 已确认并修复的诊断负担

原面板即使折叠，也每 250 ms 复制快照、整理业务与资源时间线、重新汇总资源缓存。原“暂停采集”只暂停运行时 RAF；业务 recorder、资源观察器和 UI 刷新仍在运行。场景的 `diagnostics.frames` 及详细快照也没有连接停止控制。

现在：

1. UI 每秒刷新一次，原始 RAF 采样频率、慢帧阈值与历史范围不变。刷新调度由每秒 4 次变为 1 次，这是调度数量变化，不是整页帧时下降 75%。
2. 只有展开加载时间线时才派生、排序其列表；资源快照及摘要只在资源记录变化时重算。
3. 标题旁新增 **停止检测**，折叠状态也可操作。停止后取消诊断 RAF、资源/长任务观察器、事件监听和刷新定时器，终止业务计时及场景诊断采样，并收起面板。
4. 保留最终快照用于查看和 JSON 导出。`runtime.status=stopped`、`businessPhases.enabled=false`。清理本 recorder 的 User Timing 条目，迟到的异步完成回调不再写回，未完成阶段从活动列表移除；不清理其它 recorder 的记录。
5. 风声、屋檐滴水和方位显示从诊断更新中分离，停止性能检测后仍随实际场景更新。原“暂停”明确改名为“暂停实时采样”，与完全停止区分。
6. CLI 遇到已停止的业务诊断会拒绝继续采集，防止拿冻结快照输出新的性能结论。
7. 移动端自由视角下，面板避开“选择停留位置”，展开与折叠均可继续进屋；这是浏览器回归中通过真实点击发现并修复的遮挡问题。

### 持续绘制与发热

原渲染循环跟随每个可用 RAF 提交场景，未设置绘制上限。当前移动场景样本仍约有 499 万个无方向光更新帧的三角形提交，含方向光更新的样本约 895 万个；这些包括多 pass，不能解读成屏幕上独立可见的三角形数。开启声音还增加音频处理与已解码缓冲。

用户的“运行一段时间后发热并掉帧”与持续 CPU/GPU 负载、热限制相容，但尚无真机温度或 GPU 帧时证据，**根因仍不能确定为热降频，也不能确定为内存泄漏**。原版首次进入夜景还记录了一次长停顿；它发生在切换和首次准备附近，不能单凭相关性归因声音或采集器。

新增明确的画面更新上限：默认 60 帧，另有用户主动选择的省电 30 帧和跟随屏幕。跳过的回调不更新或提交场景；动画使用距上次绘制的实际经过时间。轻微时间戳抖动不会不断累积成额外降帧，长停顿后不补画旧帧。

30 帧会降低运动连贯性；60 帧会限制高刷新率屏幕的上限。这些取舍均在界面说明，用户可独立切换。没有按温度、经过时间或观测帧率自动降低清晰度或修改配置。上限不保证设备能达到该帧率，也不会将已掉至 11–13 的设备强行提高到 30/60。

## 清晰度与配置

| 配置 | 移动端 DPR 上限 | 桌面 DPR | 更新频率 |
| --- | --- | --- | --- |
| 均衡清晰（当前默认） | 1.5 | 原桌面性能档，最高 1.6 × 0.85 | 独立选择，默认 60 |
| 完整清晰 | 2.0 | 最高 1.6 | 独立选择 |
| 稍柔和 | 保留旧档，最高 1.25 × 0.85 = 1.0625 | 最高 1.6 × 0.85 | 独立选择 |

实际还受设备 DPR 限制。默认移动端线性分辨率从 1.0625 提高至 1.5，主画面像素约为旧默认的 **1.99 倍**，会增加像素绘制与相关渲染目标的负担；因此保留旧档，并将省电帧率独立提供。雨量及几何细节不变。

在 402 × 874 CSS 像素、设备 DPR 3 的移动视口中验证：

- 旧“稍柔和”：427 × 928。
- 新“均衡清晰”：603 × 1311。
- “完整清晰”：804 × 1748。

“恢复完整效果”同时选择完整清晰、每帧动态阴影及跟随屏幕。切换帧率不会改变清晰度。室内外均走同一个配置入口，分辨率变化仍同步更新室内后处理、接触阴影及转场目标。

实时面板与 CLI 状态增加帧率配置，区分不同设置的对照条件。**RAF Hz 仍是浏览器回调率；即使场景限制为 30 帧，面板也可能显示 60 Hz。** 界面已补充该说明，不能把这个数字当作场景 FPS 改善。

## 验证与证据

- `pnpm check`：类型检查、lint、38 项测试及 LOD 产物检查通过。新增业务停止测试在旧实现上因缺少 `stop()` 失败，修复后通过；覆盖迟到的异步结束、保留历史、释放自有 User Timing、原业务返回值和异常继续传播。
- 虚拟时间验证 30 分钟持续低帧率采样的容量边界，验证销毁后没有诊断 RAF、监听器或长任务观察器残留。
- 帧率测试覆盖 60 / 120 Hz 回调、30 / 60 / 跟随屏幕、时间戳抖动、切换配置与长停顿恢复；清晰度测试覆盖低/高 DPR、移动/桌面和所有选项组合。
- `pnpm build` 和发布资源检查通过；仍有既有的大 chunk 构建提示。
- 实际 WebGL Canary 移动视口验证清晰度尺寸、帧率上限、恢复完整效果、停止按钮、停止后导出、声音及继续游览。停止后诊断定时器 **1 → 0**、诊断 RAF **1 → 0**、观察器 **2 → 0**；随后切换廊下、井边雨景、一楼堂屋，切换室内清晰度，发起新网络请求并继续等待，记录数保持不变，实际 WebGL 绘制继续。未出现页面异常、着色器错误或静态回退。
- 可重复的功能回归脚本：[mobile-runtime-smoke.mjs](../../../scripts/perf/mobile-runtime-smoke.mjs)，运行方式见 [采集工具说明](../../../scripts/perf/README.md)。它使用独立的可见 Canary 会话，402 × 874、DPR 3；通过包装诊断来源的浏览器 API 检查清理，通过 WebGL draw 调用确认场景仍在绘制。探针本身有开销，不用其计数推算正常性能。

## 真机复测边界

当前尚未在用户的 iPhone 16 Pro 上复现热状态并验证 11–13 读数消失。需要在同一视角、天气、声音状态及清晰度下，对照检测开启/停止，并分别检查 60 与省电 30 档。等待设备冷却后开始，避免把前一轮的热状态带入下一轮。保留雨景、夜景、室内及游览过程，不能以一个固定视角代表整个体验。

本阶段完成的是有证据的采集生命周期修复、诊断开销削减、移动端清晰度与可选绘制上限；真机长期帧率与发热结论仍待验证。
