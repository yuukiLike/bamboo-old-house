# 静止画面按需绘制：停止重复 GPU 提交，保留完整效果

本文记录[第六阶段审查](006-mobile-gpu-residency.md)中发现的另一项确定问题及其局部修复，不代表已经发布的独立第八阶段。父版本为 `e23daec77945c4b70d07f0956a9bcdc12232fe45`。记录日期为 2026-09-26。本次先归档文档与证据，对应实现仍在本地工作区，尚未作为生产修复提交或推送。

**已验证的收益是：静止且所有画面输入稳定后，不再重复调用 GL 绘制命令。尚未在真实 iPhone 上测量本项修改带来的 GPU 占用、发热或电池消耗变化，也没有解决或证明解决动画开启时的 10–13 Hz 问题。** 精简验证数据保存在 [tidewater-08-idle-rendering.json](evidence/tidewater-08-idle-rendering.json)。

## 问题与适用范围

此前，“静止观看”及系统“减少动态”会冻结共享动画时钟，但 `scene.ts` 的循环仍在每个通过帧率调度的 tick 调用 `renderFrame()`。在相机、天气、昼夜与后处理均已稳定时，画面仍反复提交同一批模型、阴影和后处理。冻结风雨时间并没有停止这些 GPU 工作。

修复作用于所有视角共用的场景循环，移动端和桌面端均适用。它使用已有的“静止观看”和减少动态状态，没有新增或改变画质选项；用户让风继续后，仍按原帧率设置进行动画和绘制。

## 实现与唤醒条件

本地新增的 `src/components/scene/rendering-idle.ts` 保存最近一次冻结画面的相机 world/projection 矩阵和实际 uniform 数值。只有满足下列全部条件才跳过 GPU 提交：

1. 当前为 `paused || reduced`。
2. 相机位置、方向、投影与实际动画时间、风力、雨量、湿度、秋意、昼夜混合值均未改变。比较使用精确数值，没有以距离或误差阈值忽略微小变化。
3. 天气内部没有发生会改变画面的特殊状态变化，转场也没有清除之前显示的覆盖图。
4. 没有待执行的转场 capture/reveal，没有尚未完成的室内接触阴影细化。

正常动画分支直接继续绘制，不逐帧构造大数组或 Map。矩阵、数值缓冲和 uniform 引用只初始化一次。CPU 更新与轻量 RAF 继续运行，以处理输入、设置渐变、音效 hook 和诊断；本项改动只停止不必要的 GPU 提交。

相关模块的职责如下：

| 模块 | 保留的行为与失效条件 |
| --- | --- |
| [`scene.ts`](../../../src/components/scene/scene.ts) | 输入或实际 uniform 变化时立即在下一个受原帧率设置调度的 tick 绘制。真实 resize、暂停状态变化、减少动态切换、页面恢复、复位与画面设置变化会使缓存失效。暂停时刷新最终阴影。海报导出仍显式调用完整绘制路径后读取画布。 |
| [`interior-contact.ts`](../../../src/components/scene/interior-contact.ts) | 暴露 `needsRender`。相机移动结束后继续完成原有 120 ms 停稳窗口和 100 ms 细化过程，提交最终完整 AO 后才进入静止状态；地点跳转仍在首帧使用完整细节。 |
| [`view-transition.ts`](../../../src/components/scene/view-transition.ts) | 待执行的 capture/reveal 保持绘制，保留原有 220 ms 转场。清除已显示覆盖图会增加视觉变化标记，避免稳定场景仍留下旧覆盖画面；重复空清理不会持续唤醒。 |
| [`weather.ts`](../../../src/components/scene/weather.ts) | 仅在确有蒸汽位置改变或屋檐雨滴被消耗、产生冲击时增加 `visualRevision`。常规重复 update 不无条件递增。原有 runoff 音效 hook 仍运行。 |

尤其需要区分“动画时钟冻结”和“画面已经稳定”：暂停后，用户改变昼夜或天气，原有混合与湿润程度可能仍持续渐变。此时继续绘制，直到实际输入稳定，不提前截断这些效果。减少动态状态切换也明确失效，因为该模式会直接设置部分积水和排水状态。

## 画质与诊断边界

本项修复没有减少模型或叶片、改变雨滴数量、调整纹理、降低输出尺寸、去掉主体抗锯齿，也没有缩短转场或省略最终 AO。它复用稳定画面已显示的结果；画面改变时仍执行现有完整渲染路径。无需新增画质取舍配置。

这个结论由输入依赖审查、真实天气状态测试、室内细化测试及浏览器绘制检查共同支持。截图目视确认静止后仍保留完整场景，没有黑帧；本轮没有进行修改前后的逐像素图片差分，因此不将上述检查写成所有设备上的像素一致性实测。

诊断保留原有 RAF 含义：**静止后读数接近 60 Hz，不表示画面每秒重新绘制了 60 帧。** `cpuUpdateMs` / `cpuRenderSubmitMs` 按最近 15 个通过帧率调度的更新 tick 求平均，未提交绘制的 tick 以 0 提交耗时参与平均。更新诊断时，若该 tick 未绘制，应用的 `drawCalls` / `triangles` 记为 0，不冒用上一次绘制的数量；Three 自身 `renderer.info` 的记录没有被篡改。这些值均不是 GPU 执行时间。

- 本地新增的 `tests/rain-shelter-lifecycle.test.ts` 增加 **24 组冻结验证**：移动端/桌面端 × 普通暂停/减少动态 × 雨量 `0/.42/1` × 初始状态/先运行 120 ticks。每组第一次冻结 update 后继续更新 60 次，几何属性、可见性、drawRange/instanceCount、真实 shader 和表面天气 uniforms、`visualRevision` 均保持不变。雨天样本确认蒸汽实际可见。

## 尚未确认的收益与后续验收

本地浏览器已证明稳定静止场景不再重复提交 GL 绘制，以及交互和现有效果仍能完成。它没有测量真实 iPhone 的 GPU 利用率、GPU 执行时间、功耗、电池消耗、温度或持续运行后的频率恢复。

真实 iPhone 下一步应在同一视角、天气与清晰度下对照动画开启、稳定暂停及恢复播放，确认停止的是实际绘制提交，观察系统 GPU/进程负载和热状态变化；诊断面板的 RAF 数字只能作为调度信息。若暂停时湿度或昼夜尚在变化，应等原有渐变结束后再进行“稳定静止”对照。

动画开启时继续使用原有模型与绘制规模。因此，本项修复不能作为 iPhone 动画运行后降到 10–13 Hz 已解决的依据；该问题的真机证据、排除项和未确认假设继续由[第六阶段报告](006-mobile-gpu-residency.md)维护。
