# iPhone 持续掉帧调查检查点

记录日期：2026-09-26。详细实验见[第六阶段报告](./optimizations/006-mobile-gpu-residency.md)，系列进度见[优化记录](./optimization-log.md)。本页用于保留当前判断与下一步入口，不把尚未完成的根因调查写成修复完成。

## 当前结论

**iPhone 16 Pro 上，正常播放约 20–30 秒后降至 10–13 Hz 的问题仍未解决。** 已连接用户的真实手机完成网页探针、系统日志、原生进程 CPU / 内存及系统图形计数器采集。Mac 的流畅表现、单次暂时恢复和已有资源优化，都不能替代 iPhone 持续运行的验收。

目前证据更支持继续调查**绘制命令完成路径和持续 GPU 负载**，不支持仅用“性能检测数据越积越多”解释。还没有取得 GPU / CPU 的实时频率，不能宣布已经证明某种降频机制或固定 10 Hz 的系统限制。

临时原生采集已经结束；有损几何、风动关闭、抗锯齿关闭及临时 fence 等探针均未加入产品。后续恢复测试时先核对实际页面与构建，不要求用户一直保持手机静止。

## 已检查但未形成持续恢复的方向

关闭网页 CSS 背景模糊、默认画布抗锯齿、风动画、抑制动态 buffer 上传，以及把静态属性展开成 Float32，都没有在已记录的对照中恢复持续流畅。短时测试只作短时结论；例如网页 CSS 模糊测试没有隔离 Safari 自身的原生工具栏合成。

释放雨效烘焙后的约 71.11 MiB 索引容量，消除了确定的无用驻留，但新版真机仍约在 23–27 秒从 32 降至 11 Hz。71.11 MiB 是解除引用的数组容量，不是测得的 iPhone RSS 降幅。

Babylon 的 WebGPU bind group 缓存泄漏与本项目的 Three WebGL 路径不同；相似的 iPhone 延迟掉帧报告值得参考，但外部 WebGL / WebGPU 对照尚未完成有效采样。Flutter 液态玻璃 issue 也没有证明本项目命中同一缺陷。原始帖子、源码链接及适用边界集中在[详细报告](./optimizations/006-mobile-gpu-residency.md)。

## 接下来最有区分力的验证

1. 在同一构建、相机、天气及实际画布尺寸下，用原生图形计数器验证“正常播放 → 静止观看且画面稳定 → 恢复播放”。同时记录实际 GL 提交、页面 RAF 和主机时间，确认静止修复确实降低 GPU 工作，并观察恢复后的退化时间。静止时 RAF 高不等于画面每秒重画 60 次。
2. 对时间相关退化继续取得可解释的 GPU / 驱动证据。现有工具没有带定义的实时 GPU MHz / DVFS 接口；可先只读发现系统 trace 的事件名，再决定是否有足够字段解释价值，避免直接启动高开销全量追踪。
3. 若继续验证上游线索，采用能实际加载完成的同场景 WebGL / WebGPU 对照，核实真正创建的后端。Safari 原生合成对照须保持实际像素尺寸；这些目前都是待验证项。

每轮保留正常与退化阶段，不在掉帧后才清空采集。测试以固定时长结束并恢复原模型与画质。完整呈现始终保留；任何减少模型、雨效或清晰度的选择都必须明确可配置，不能混入无损收益。
