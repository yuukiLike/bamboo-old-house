## 目标

建立“本地开发 → 线上预览 → 正式发布 → 出错回退”的最小流程，为产品宣发和后续迭代提供稳定入口，也为性能基线提供可追溯的线上版本。

## 已确认的方向

- 先建立本 issue，并将四个 issue 与计划推到独立的问题集合分支，然后开始实现。
- 采用本地开发、线上预览和正式站三层；首版不单独建设线上 dev 或灰度分流。
- 优先使用现有托管平台的版本预览地址，固定的测试子域名作为可选项。
- 正式发布保留明确的人工触发步骤，能够追溯发布版本并回退。

## 已查明的现状

- 项目静态导出到 `dist/client`，`wrangler.static.jsonc` 配置 Cloudflare Worker `bamboo-old-house`。
- `main` 提交存在成功的 Cloudflare Workers Builds 检查，说明已有平台侧 Git 集成；其具体分支、构建与发布设置仍需核对。
- 仓库另有 `netlify.toml`，文件存在不代表当前正式站使用 Netlify；实现时沿用实际部署平台，不并行引入第二条上线渠道。
- GitHub Actions 的 `Checks` 包含类型、lint、测试、LOD 一致性和构建。当前 workflow 未包含部署步骤。
- 资源使用 `/models/`、`/audio/` 等根路径，预览采用独立主机名，避免子路径部署影响加载。

## 实现范围

1. 核对实际生产地址、生产分支、自动构建与自动上线规则，并记录。
2. 功能分支可以上传不影响正式流量的版本，生成可识别的预览链接。
3. 为每个候选版本关联提交 SHA、构建或部署版本 ID；性能复测采用固定版本 URL，移动别名仅作为方便入口。
4. `main` 的候选版本完成检查与验收后，人工发布已验证的版本，避免重新构建另一份内容。
5. 提供明确版本的回退方式，页面、脚本与模型等静态资源一起恢复；记录历史版本保留限制。
6. 预览索引策略不影响正式站；默认预览可通过链接访问，需要私有访问时再配置访问控制。
7. 完成发布文档与必要的配置校验，记录首次真实预览验证结果。

普通 PR、问题集合分支推送与预览上传不得切换正式站。正式版本切换与回退演练使用明确选定的版本和时机，不以当前线上用户为测试对象。

## 验收标准

- [ ] 记录实际托管平台、正式地址、生产分支与触发规则。
- [ ] 推送功能分支可得到线上预览，正式部署版本保持不变。
- [ ] 预览可正常加载页面、3D 模型、声音和其他静态资源。
- [ ] 预览与候选版本可追溯至 Git 提交和部署 ID。
- [ ] 正式发布要求检查通过、明确选择已验收候选版本，并由人工触发。
- [ ] 回退必须显式选择历史正式版本，文档说明可用版本范围及资源恢复方式。
- [ ] 预览搜索索引设置不会被带入正式站；若需要限制访问，明确其独立配置。
- [ ] 部署凭据不进入 Git，未信任的 fork PR 无法获取发布凭据或触发生产变更。
- [ ] 保存实际预览、发布及回退的验证证据；尚未执行的验证保持未勾选。

## 待核对

- 当前正式地址、Cloudflare 控制台的分支和部署命令。
- 现有授权是否支持预览上传、版本查询与部署管理。
- 是否需要自定义预览子域名或访问控制；首版优先使用平台默认地址。

## 实施进展

- [部署说明](../deployment.md) 已提供控制台过渡设置、最终配置、候选验收、手动发布和明确版本回退步骤。
- `build:release` 运行质量检查并构建，记录来源与产物摘要；`deploy:preview` 核对产物后仅上传版本。
- Wrangler 开启版本预览；预览专用 `noindex` 规则保留正式地址的索引行为。
- GitHub CI 检查静态文件上限，部署凭据仍由现有 Workers Builds 管理。
- 用户明确由自己操作 Cloudflare，因此实际地址、分支规则、真实预览、正式切换与回退验收仍保持未勾选。
