## 目标与完成边界


使用 Chrome DevTools、[RenaudRohlinger/stats-gl](https://github.com/RenaudRohlinger/stats-gl) 和 Three.js 原生统计，建立当前版本在代表性场景中的可复现基线。定位实际耗时过程，再决定优化顺序。

用户明确要求：每次优化开始前，记录拟优化的具体过程、细节和依据；优化后记录实际改变、同条件复测结果及视觉影响。无收益、失败和回退的尝试也保留记录。

本 issue 的完成边界是测量方法、首份基线、证据支持的瓶颈清单和优化记录流程。后续优化关联本 issue，按具体瓶颈拆分小 issue 或 PR，不以“所有性能问题都解决”为关闭条件。

## 一、固定基线与比较条件

- 初始参考版本：`v0.1.0` / `dbd8e74`。同时记录完整提交 SHA、资源版本或哈希、依赖锁文件和构建命令。
- 使用生产构建测量；本地预览与线上网络加载分别报告，不混用开发服务器与生产构建结果。
- 若需要补充监测代码，单独记录监测提交及其基于的产品提交；监测阶段不夹带性能优化。
- 保存原始参考基线，后续结果另存为新记录。建立新版本基线时明确版本和原因，不覆盖旧数据。
- 每个测量配置记录设备型号、CPU/GPU、内存、操作系统、浏览器及版本、图形后端、工具版本、硬件加速状态、屏幕刷新率、电源模式及明显的温度/后台负载变化。
- 固定视口、浏览器缩放、DPR、画布实际像素尺寸、相机位置/方向/FOV、路径位置、时段、天气、声音、动画与减少动态设置。
- 记录网络/CPU 限速、缓存状态，以及 DevTools、统计面板和采样工具的开关状态。
- 桌面 Chrome 与真实移动设备分别建立基线。设备模式和 CPU 限速只作为模拟配置，不当成真实手机 GPU 性能。[Chrome DevTools 对限速的说明](https://developer.chrome.com/docs/devtools/performance/reference#throttle-the-cpu-while-recording)

建议首轮覆盖一台固定桌面设备和一台真实手机。具体机型、移动浏览器和性能目标在采集前确定；缺少设备时标记覆盖缺口，不用模拟结果填充。

## 二、工具分工与指标口径

| 工具 | 用途 | 需要留下的证据 |
| --- | --- | --- |
| Chrome DevTools Performance | 首次加载、主线程耗时、长任务、动画与交互停顿；按 Call Tree / Bottom-up 定位函数及调用链 | 保存 trace、选择的时间区间、函数 self/total time、触发步骤 |
| Chrome DevTools Network | 区分模型/纹理/脚本下载与后续解码、构建耗时 | 缓存/限速配置、请求瀑布与传输量、必要时 HAR |
| Chrome DevTools Memory | 观察重复切换后的 JS 堆、对象分配与保留链、回收行为 | 明确循环步骤，保留前后快照或分配记录 |
| stats-gl | 观察 FPS、所监测代码区间的 CPU 时间，以及设备支持时的 GPU query 时间 | 精确版本、接入位置、采样范围、可用指标及原始记录 |
| Three.js `renderer.info` | 每帧 draw calls、绘制三角形数量、活动几何体/纹理数量、program 数量 | 统计重置位置、整帧或具体 pass 范围、场景状态 |
| 现有 `window.__BAMBOO__` 诊断 | 复用帧间隔、场景状态与已有渲染计数，补充场景分段和导出 | 标注现有指标定义，按固定场景保存原始样本 |

Performance 的主线程调用树用于寻找代码时间花在哪里；Memory 快照用于解释对象为何仍被保留。JS 堆、浏览器进程占用和显存是不同指标，不相互替代。[Performance 参考](https://developer.chrome.com/docs/devtools/performance/reference)、[内存分析说明](https://developer.chrome.com/docs/devtools/memory-problems)

`renderer.info.memory` 的几何体和纹理字段是对象数量，不是显存字节。多 pass 渲染必须统一整帧统计边界；调用次数和三角形数不能直接当成 GPU 耗时。[Three.js WebGLRenderer 文档](https://threejs.org/docs/pages/WebGLRenderer.html#info)

### stats-gl 的接入边界

- 当前核对的上游源码版本为 `dae82f5a4a14d19a3ec21bc47b28a491a668a036`（package 版本 `4.2.3`），尚未安装到本项目。正式接入时固定并重新核对实际版本。
- Three.js WebGL 自动接入包围的是 `renderer.render()`，不会自动覆盖其外部的场景更新；多 pass 情况需核实监测范围和累积方式。[接入源码](https://github.com/RenaudRohlinger/stats-gl/blob/dae82f5a4a14d19a3ec21bc47b28a491a668a036/lib/core.ts#L450-L536)
- WebGL2 GPU 计时依赖 `EXT_disjoint_timer_query_webgl2`。查询未完成、不支持扩展或出现 disjoint 时，不报告有效耗时。[Khronos 扩展规范](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)
- 当前实现会在一次更新中累计已经异步返回的 GPU query，不能假定它与同一时刻 CPU 样本一一对应。面板另有平滑；未经验证，不用面板值计算“逐帧 GPU p95”，也不把 CPU 和 GPU 数值相加作为整帧耗时。[GPU query 源码](https://github.com/RenaudRohlinger/stats-gl/blob/dae82f5a4a14d19a3ec21bc47b28a491a668a036/lib/core.ts#L427-L449)、[面板更新源码](https://github.com/RenaudRohlinger/stats-gl/blob/dae82f5a4a14d19a3ec21bc47b28a491a668a036/lib/main.ts#L294-L349)

### 现有项目诊断的限制

- `startupMs` 从进入 `createScene()` 开始，不含之前的动态模块导入，也不等于画面已呈现或控件已可操作。
- `frames` 只跳过最初 30 帧，上限 15,000 个样本，切场景不会自动分段；大部分场景状态和计数每 15 帧才更新一次。需要重新规定采样窗口，不能直接把整段混合历史当作某个场景的基线。
- 当前 `renderFrame()` 已在开始时重置 `renderer.info`，可以累计整帧各 pass；接入工具应保留这一口径。
- `window.__BAMBOO__` 存在不表示初始化结束；`getPoster()` 会额外绘制并同步导图，只在性能采样窗口外获取取景参考图。
- 天气湿润和积水依赖之前的操作，现有 `reset()` 不清空这些历史。场景准备流程需要固定，不能只记录最终天气按钮。
- 移动质量档在场景创建时确定，单纯缩小已打开的桌面窗口不等于重新创建移动场景。首次进屋后常驻的室内资源增加也不等于泄漏，需观察重复循环是否持续增长。

### 必须区分的时间

- **帧间隔**：相邻 RAF 时间戳的间隔，反映调度与卡顿；报告中位数、p95、p99和超过约定帧预算的比例。它不是某个函数的执行时间，也不是严格的屏幕呈现时间。
- **CPU 时间**：明确被包围的代码区间。至少区分场景更新与渲染命令提交，不把单个 `renderer.render()` 的耗时称为整个应用 CPU 耗时。
- **GPU 时间**：来自支持的计时查询；标明查询边界、有效样本数量和异步读取规则。缺失或无效结果记 N/A，不能记为 0。
- **首帧与可交互时间**：首次显示有效 3D 画面、控件可响应分别定义起止事件；网页 load、LCP 和现有 `startupMs` 不能直接替代。
- **首次使用开销**：首次进屋、首次夜间灯光/阴影准备和天气启动单独记录；稳定运行的暖机样本不能掩盖这些停顿。

先测量基线波动，再确定项目自己的回归阈值。60 Hz 下约 16.7 ms、30 FPS 下约 33.3 ms 可作帧预算参考，不代表当前项目已达到这些目标。

## 三、代表性场景

| 场景 ID | 固定操作 | 重点观察 |
| --- | --- | --- |
| load-cold / load-warm | 明确缓存条件，打开初始场景；冷/暖加载分别重复 | 下载、解码、场景构建、首个有效 3D 帧、可交互时间 |
| walk | 按固定耗时走完五段路径，在固定位置停留 | 帧间隔、更新开销、植被/阴影绘制与相机移动 |
| porch | 固定木廊视角，分别观察白天与傍晚 | 稳定渲染、风动画、画布分辨率影响 |
| interior-first / interior-steady | 从同一屋外位置首次进屋；预热后重复同一室内视角，分别持续转动与停下 | 首次准备峰值、移动/静止接触阴影、缓存及多 pass 成本 |
| night-moon | 切至夜间与望月视角，稳定后记录 | 切换峰值、灯光/阴影、夜间持续渲染 |
| weather | 固定井边雨景及林间大风，分别记录首次切换与稳定状态 | 雨、湿润、落叶、风及可选声音的工作量 |
| lifecycle | 固定次数往返室内外、昼夜与天气；另测挂载/销毁、加载中退出与后台返回 | 资源数量是否持续增长、JS 保留对象、监听器/RAF 清理 |

每个场景保存完整状态与操作时间线。自然动画造成的变化用同条件重复测量评估，不能选择性截取最好的一段。

新功能合入后，将截图进入/退出/导出和语言切换加入对应场景的回归检查；当前版本不存在的功能记“不适用”。

## 四、采集流程

1. 确认版本、设备和构建配置，保存场景状态与一张取景参考图。
2. 冷启动及首次使用单独录制，不预热；说明“冷缓存”具体清除了什么，未控制的驱动/着色器缓存注明未知。
3. 稳定运行场景建议至少暖机 10 秒，并等待切换、光照与天气状态稳定后采样。每轮采样 30 秒，每个配置至少 3 轮；记录实际时长、样本数与轮间波动。
4. 轻量采样用于可比较的帧数据；详细 DevTools 录制和内存分析另跑，用于归因。基线与候选改动使用相同工具配置，并用关闭重型分析工具的复测检查监测开销。
5. 帧数据从原始样本计算分位数，先逐轮汇总，再报告各轮结果与波动。短暂卡顿与稳定状态分开报告，不混合成一个平均 FPS。
6. 针对一个候选优化，用相同设备、场景、资源与画质做 A/B，必要时再测 A，排除温度或后台负载漂移。
7. 60 Hz、120 Hz、不同画布尺寸和不同设备各自比较。改变 DPR、阴影质量、视距或效果数量时，单独注明画质取舍，不能作为等画质收益。

缺失指标保留为 N/A，并说明工具、设备或采样原因。基线阶段不预先宣称某个模块是瓶颈。

## 五、每次优化必须先写的记录

建议每次优化在 `docs/performance/optimizations/<编号>-<主题>.md` 保存一份记录，并关联 issue、PR 和完整提交 SHA。先保存并提交“优化前”部分，或先发布到关联 issue，再开始优化代码；不在完成后倒填原始假设。

以下模板同时记录“计划改变什么”与“最终实际改变什么”：

```markdown
# PERF-XXX：具体的优化过程

## 优化前（动手前填写）
- 日期、作者、issue：
- 基线版本 / 本次改动前提交 / 测量配置 ID：
- 触发场景和可重复操作：
- 用户可见问题：
- 具体过程：文件、函数、调用链或渲染 pass：
- 当前工作细节：何时触发、每帧/每次切换执行多少次、处理什么数据、
  分配什么资源、资源在何时复用或释放：
- 原始证据：trace 文件、时间区间、样本记录、相关计数：
- 已确认事实 / 尚未证实的瓶颈假设：
- 计划改动：准备减少、合并、推迟、复用或取消哪一步，以及理由：
- 预期改善的指标、判定阈值和已知测量波动：
- 必须保持的画面与交互 / 需明确确认的画质取舍：
- 复测步骤与失败时的回退方式：

## 优化后（完成后补充）
- 实际改动、涉及文件/函数、提交和 PR：
- 与原计划不同的地方及原因：
- 对照结果：配置、指标、单位、before、after、绝对/相对差值、各轮波动：
- 过程变化证据：调用次数、遍历量、分配次数、pass 或资源生命周期变化：
- 原始记录与同机位画面对照：
- 其他代表场景、交互和生命周期的回归结果：
- 结论：保留 / 无明显收益 / 回退 / 证据不足：
- 局限与下一步：
```

“优化了竹林性能”不足以说明改动。记录应能回答：改的是每帧遍历、实例更新、阴影绘制、shader、纹理解码、后处理还是资源释放；修改前具体做了什么，修改后省掉或改变了什么；测量结果是否支持这一解释。

一次 PR 尽量验证一个主要假设。优化无收益或产生画面/交互回归时，保存记录并回退代码，避免重复尝试同一无效方案。

## 六、证据保存与验收

测量实施时，建议将协议、环境、汇总结果和优化记录放入 `docs/performance/`。原始 trace、样本和画面对照按 run ID 存档到可长期访问的位置，在报告中记录链接、采集时间和文件哈希；本地临时路径不能成为唯一证据。避免把大量 trace 二进制或视频直接提交到源码仓库。

- [ ] 明确参考提交、生产构建、资源和工具版本。
- [ ] 代表性场景具备可重复的操作和完整状态记录。
- [ ] 目标设备分别有冷/暖加载、首次使用、稳定帧表现及生命周期数据；未覆盖项注明原因。
- [ ] CPU、GPU、帧间隔、渲染计数和内存指标边界清楚，无缺失值伪装成 0。
- [ ] 原始样本、trace 和汇总结果可追溯，重复轮次与波动被保留。
- [ ] 检查采样工具自身开销；监测默认关闭，不成为普通用户界面的一部分。
- [ ] 根据测量列出瓶颈证据、候选优化和优先级；区分事实与推测。
- [ ] 每次优化的开始条件是已保存优化前记录；合并条件是已有同条件复测和画面/交互回归结论。
- [ ] 基线与第一批优化任务分别关联 PR，初始参考数据不被覆盖。
